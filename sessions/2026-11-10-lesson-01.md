## Fourth learner response: asks how to use row locks

Evidence: proposes moving coordination to database rows after the two-instance scenario and explicitly requests teaching about the mechanism. This does not independently establish understanding of Java monitor scope or the SQL implementation.

Teaching: acquire the appropriate exclusive row lock with the initial locking read, before the balance decision, rather than obtaining shared locks and upgrading later. Use a PostgreSQL READ COMMITTED example with SELECT ... FOR UPDATE within one transaction. The second locking read waits; after the first commits it can return the updated row. Keep the read, validation, update, and commit in one transaction. Ordinary nonlocking readers are not necessarily blocked. No claim of universal deadlock prevention: other rows/resources and reversed acquisition order can reintroduce cycles.
